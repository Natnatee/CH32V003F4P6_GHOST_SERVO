# Receiver: IR 38kHz → MG90S

## โค้ดปัจจุบัน: IR (แทน RF)
- ตัวรับ IR **demodulated 38kHz, OUT Active LOW** → PC4 ขาชิป14 (floating input); idle HIGH, พบพาหะ LOW โค้ดกลับ polarity ก่อนถอดรหัส
- ไม่ใช้ photodiode เปล่า/โมดูล obstacle detector แทนตัวรับชนิดนี้; ชื่อรุ่นจริงยังไม่ทราบ ต้องตรวจความถี่และลำดับ VCC/GND/OUT ตามโมดูล
- VCC ตัวรับ IR ตามสเปกรุ่นจริง ไม่อิงว่าตัวรับ RF เก่าใช้5V แล้วทุกตัวจะใช้ได้; หาก MCU5V แต่ OUT3.3V ต้องตรวจเกณฑ์ HIGH/แปลงระดับให้เหมาะสม ห้ามต่อ12V
- ใช้ PC4 ขาชิป14 เดิม ห้ามต่อ DATA โมดูล RF พ่วงอยู่; Servo signal PD2 ขาชิป19 เดิม
- GND ร่วมเฉพาะอุปกรณ์ภายในแต่ละฝั่ง ไม่ต้องลาก GND ข้ามฝั่ง IR
- คง servo ประมาณ160° pulse600–2380us; startup HOME1s → ออก → ค้าง5s → กลับ → READY; เมื่อได้รับคำสั่งยืนยัน ออก/ค้าง5s/กลับ/พัก10s
- รหัส A5C33C ต้องตรงสองแพ็กเก็ตใน500ms; normal log เฉพาะเหตุการณ์ `[IR RX] STATE/CONFIRMED A5C33C`

แฟลชใช้งานจริง:
```bash
pio run -d receiver -e ch32v003f4p6 -t upload
```

ทดสอบ IR โดยงด servo pulse:
```bash
pio run -d receiver -e ir_test -t upload
```

เปิด log ผ่าน SDI:
```bash
/c/Users/natna/.platformio/packages/tool-minichlink/minichlink -T
```

ir_test แสดง `[IRTEST]` และ `[US]`; `mark=1` คือ IR receiver OUT LOW (กำลังรับ burst), mark=0 คือ idle ไม่ใช่ระดับไฟตรงPC4; H/L ในสถิติคือระยะ mark/space หลังกลับ polarity รูปแบบตัวนับเหมือนเดิม

ต้องแฟลช IR ทั้งสองฝั่งและหัน LED ไปหาตัวรับ ทดสอบจริงยังไม่ยืนยัน ไม่ได้วัด carrier ด้วยออสซิลโลสโคป โหมด rf_test เดิมเปลี่ยนชื่อเป็น ir_test แล้ว

ผังขาชิปและเรื่อง servo ด้านล่างยังใช้อ้างอิงได้ แต่รายละเอียด RF/คำสั่ง rf_test เป็นประวัติเก่า ไม่ใช่โค้ดปัจจุบัน

## ประวัติการทดสอบ RF ก่อนเปลี่ยนเป็น IRแล้ว

## ช่วงเซอร์โวปัจจุบัน: ประมาณ 160°
โหมดปกติเปลี่ยน HOME/OUT เป็น **600–2380µs** ทั้ง startup และคำสั่ง RF (แทน 1000–2000µs ในบันทึกเดิมด้านล่าง) กวาดขาละประมาณ 3.56s ค้าง 5s กลับแล้วพัก 10s ตามเดิม; startup กลับแล้ว READY ไม่พัก 10s

ประมาณมุมจากผลเดิม 500µs ≈45° ยังไม่ยืนยันช่วงใหม่จริง จุด home เปลี่ยนจากเดิม ต้องถอดโหลด/แขนกลทดสอบก่อน หากชนสุด คราง หรือร้อนให้ตัดไฟแล้วลดช่วง pulse ไม่ฝืนให้ถึง 160°; rf_test ยังไม่สร้าง pulse เซอร์โว

โปรเจกต์ CH32V003F4P6 + ch32v003fun แยกจากโค้ดทดสอบเดิม

## โหมดทดสอบ RF ล้วน (`rf_test`)
แฟลชทั้งสองฝั่งเป็น `rf_test` โดยต่อโปรแกรมเมอร์กับบอร์ดเป้าหมายทีละตัว:
```bash
pio run -d transmitter -e rf_test -t upload
pio run -d receiver -e rf_test -t upload
```
จากนั้นต่อ WCH-LinkE กับตัวรับ เปิด monitor ตามคำสั่งด้านล่าง โหมดนี้ไม่สร้าง pulse เซอร์โว (PD2 LOW) ไม่มี startup test แนะนำถอดเซอร์โวระหว่างทดสอบ ไม่มีการเชื่อมสายหรือ GND ข้ามฝั่ง แต่ GND อุปกรณ์ภายในแต่ละฝั่งต้องร่วมกัน

ฝั่งส่งส่ง A5C33C ชุดละ 8 แพ็กเก็ต (~0.39s) เงียบ 1s ไม่ใช้ PIR; LED PC2 ติดช่วงส่ง ดับช่วงเงียบ

ฝั่งรับสรุปประมาณวินาทีละครั้ง:
- `[RFTEST]`: `dt` ช่วงเวลารายงาน, `dE` จำนวนขอบที่เพิ่มในช่วงนั้น, `edges/sync/bad/packets/match` ตัวนับสะสม, `last` รหัส 24 บิตล่าสุด, `maxbits` จำนวนบิตที่ไกลที่สุดหลัง sync
- `[US]`: `H/L` ความกว้าง HIGH/LOW ล่าสุด หน่วย µs (อาจไม่ใช่ pulse คู่เดียวกัน), `failH/failL` คู่ที่ทำให้ decoder พลาดล่าสุด, `bits` บิตที่ถอดได้ก่อนพลาดครั้งนั้น
- `Hbin/Lbin` ตัวนับสะสม 4 ช่วง: <100, 100–600, 601–1300, >1300µs; ข้อมูลต้นเครื่องช่วงแรกอาจเป็น pulse ที่จับไม่ครบ
- `fail*`, `last`, `maxbits` ค้างค่าล่าสุดได้ ไม่ได้แปลว่ามีเหตุการณ์ใหม่ทุกบรรทัด
- ค่าที่ส่งคาด H/L 300/900 หรือ 900/300µs, sync 300/9300µs; เป้าหมาย `last=A5C33C` และ `match` เพิ่มซ้ำ ๆ ไม่ใช่แค่ sync เพิ่ม
- เปิด/ปิดไฟตัวส่งเทียบ log โดยไม่รีเซ็ตตัวรับ; วางห่างประมาณ 1m และใส่เสาอากาศ 17.3cm ที่ ANT ตามโมดูลจริง
- RF test ใช้เกณฑ์บิตทดลอง: HIGH+LOW รวม 900–1500µs, แต่ละด้าน 80–1300µs; ด้านสั้นต้องไม่เกิน 80% ของด้านยาว HIGH ยาวกว่า = 1, LOW ยาวกว่า = 0 ยังตรวจรหัส A5C33C สองแพ็กเก็ตใน 500ms; sync และ protocol ไม่เปลี่ยน โหมดปกติใช้เกณฑ์เดียวกันแล้ว หลังผู้ใช้ยืนยันรับ A5C33C และ match เพิ่มต่อเนื่อง
- timing จาก polling เป็นข้อมูลประกอบ ไม่แทนออสซิลโลสโคป การ format สรุปอาจพลาดบางขอบได้ เกณฑ์ใหม่นี้ยังต้องทดสอบจริง ไม่ใช่การยืนยันว่าโมดูลทำงาน

กลับโหมดใช้งานเดิม:
```bash
pio run -d transmitter -e ch32v003f4p6 -t upload
pio run -d receiver -e ch32v003f4p6 -t upload
```
ค่าปริยาย `pio run` ยังเป็นโหมดเดิม ผู้ใช้ยืนยัน RF test รับ A5C33C ได้ซ้ำต่อเนื่องหลังย้าย DATA ตัวส่งจาก PC0 (ขา 10) ไป PC4 (ขา 14); โหมดปกติหลังรวม decoder ต้องทดสอบ PIR/servo ร่วมกันอีกครั้ง

## การต่อสาย

```text
CH32V003F4P6 TSSOP20 (มองด้านบน)
           +---U---+
 PD4     1 |       | 20 PD3
 PD5     2 |       | 19 PD2 --> MG90S Signal
 PD6     3 |       | 18 PD1 --> WCH-LinkE SDI
 PD7     4 |       | 17 PC7
 PA1     5 |       | 16 PC6
 PA2     6 |       | 15 PC5
 VSS     7 |       | 14 PC4 <-- RF DATA (MCU 5V ต่อตรง)
 PD0     8 |       | 13 PC3
 VDD     9 |       | 12 PC2
 PC0    10 |       | 11 PC1
           +-------+
```

ผังนี้เป็นขาชิป ไม่ใช่ตำแหน่ง header ของเดฟบอร์ด ให้ดูชื่อ GPIO บนบอร์ดจริง

- ผู้ใช้ยืนยัน MCU ฝั่งรับเลี้ยง 5V ไม่ใช่ 3.3V; ห้ามต่อขา 3.3V ของ WCH-LinkE ซ้อน VDD 5V ใช้ SDI/GND ตามการต่อที่แฟลชได้
- MX-RM-5V: VCC = 5V, GND ร่วมภายในฝั่งรับ, DATA → PC4 (floating input) ตรง สำหรับ MCU ที่เลี้ยง 5V
- เอาตัวแบ่ง 10kΩ/18kΩ ที่เคยแนะนำตอนเข้าใจว่า MCU ใช้ 3.3V ออก; หากเปลี่ยนแรงดัน MCU ต้องตรวจระดับลอจิกใหม่
- ตรวจแรงดันจริงก่อนต่อ หากตัวรับมี DATA สองขา ใช้เพียงขาเดียวและยืนยันจากสกรีน/วงจร ไม่เดาลำดับขาจากภาพสินค้า
- MG90S: ส้ม/เหลือง → PD2 (Output Push-Pull), แดง → ไฟแยก +5V, น้ำตาล → GND ร่วม
- ไฟแยก 5V แนะนำอย่างน้อย 1A; ห้ามเลี้ยงเซอร์โวจาก 3.3V ของ WCH-LinkE
- แนะนำ C 470–1000µF คร่อมไฟเซอร์โวใกล้จุดต่อ (ดูขั้วให้ถูก) และ C 100nF ใกล้ตัวรับ แยกทางสายไฟเซอร์โวจาก RF
- เสาอากาศสายตรงประมาณ 17.3cm ที่ ANT ของทั้งสองโมดูลช่วยเรื่องระยะ; ไม่ต่อเข้าขา DATA


## Startup test และ SDI log
เปิดเครื่องสั่ง HOME 1000µs ค้าง 1s → ค่อย ๆ ออก 2000µs ใน 2s (คาดประมาณ 90°) → ค้าง 5s → ค่อย ๆ กลับใน 2s → READY ทันที ไม่มีพัก 10s ในรอบ startup ทดลองแบบไม่ติดโหลดก่อน

เปิด SDI monitor หลังแฟลช (ไม่ใช้ Serial COM):
```bash
/c/Users/natna/.platformio/packages/tool-minichlink/minichlink -T
```
Ctrl+C เพื่อหยุด; หยุด monitor ก่อนแฟลชรอบใหม่

โหมดปกติพิมพ์เฉพาะเมื่อสถานะเปลี่ยนหรือยืนยันคำสั่งสำเร็จ: `[RX] STATE/CONFIRMED A5C33C test=... state=... pulse=... match=...` ไม่พิมพ์ noise ทุกวินาที รายละเอียดตัวนับด้านล่างใช้ในโหมด rf_test
- `test=1`: กำลังทดสอบตอนเปิดเครื่อง; `state=READY`: รอ RF, OUT/HOLD/HOME/WAIT10: ลำดับเซอร์โว
- `edges`: จำนวนขอบสัญญาณ PC4 สะสม (noise ก็ทำให้เพิ่มได้)
- `sync`: พบ sync ที่เข้าเกณฑ์, `bad`: pulse pair ผิดหลัง sync
- `packets`: ถอดครบ 24 bits, `last`: รหัสล่าสุดฐานสิบหก ควรเป็น A5C33C
- `match`: จำนวนครั้งที่ยืนยันคำสั่งสองแพ็กเก็ตได้; ถอดรหัสเฉพาะ READY
- ตัวนับสะสม ไม่ใช่ค่าต่อวินาที; log ส่งแบบไม่รอ host ผ่าน DMDATA และ format เฉพาะช่วง servo LOW/นอกแพ็กเก็ต RF สรุปที่ยังส่งไม่หมดจะไม่ถูกเขียนทับ เมื่อไม่ได้เปิด monitor จะไม่ขวาง servo
- การทำ polling และ format log ยังต้องตรวจ timing บนฮาร์ดแวร์จริง ไม่ใช่เครื่องวิเคราะห์ RF และไม่มีข้อความก็ยังสรุปว่า RF ไม่ทำงานไม่ได้

## การทำงาน

1. รับรหัส `0xA5C33C` 24-bit MSB-first ถูกต้องสองแพ็กเก็ตภายใน 500ms
2. ค่อย ๆ หมุน pulse 1000 → 2000µs ประมาณ 2 วินาที (คาดประมาณ 90° จากผลเดิมที่ 1000–1500µs ได้ 45°)
3. ค้างปลายทาง 5 วินาที
4. ค่อย ๆ หมุนกลับ pulse 1000µs ประมาณ 2 วินาที
5. พัก 10 วินาที แล้วพร้อมรับใหม่ หาก PIR ยัง HIGH และฝั่งส่งยังส่งอยู่จะเริ่มรอบใหม่ได้

คำสั่งระหว่างทำงาน/พักถูกทิ้ง ไม่เข้าคิว เปิดเครื่องจะทดสอบออกและกลับตามหัวข้อ Startup test จึงต้องทดสอบแบบถอดโหลดก่อน ไม่มีการจำตำแหน่งจริงหรือ feedback

RF และ servo ใช้ polling แบบไม่บล็อก ไม่มี printf ในลูป ช่วง pulse เป็นค่าทดลอง ไม่ใช่การยืนยันมุมจริง หากชนสุดหรือครางให้ตัดไฟและปรับช่วง

Protocol: sync HIGH300/LOW9300µs, bit0 HIGH300/LOW900µs, bit1 HIGH900/LOW300µs, จบ HIGH300/LOW9300µs ตรงกับ `../transmitter` เป็นรหัสคงที่ช่วยกรอง noise ไม่ใช่ระบบเข้ารหัสหรือป้องกัน replay
